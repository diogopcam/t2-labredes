1. VISÃO GERAL DO PROTOCOLO
================================================================

O SRTP (Simple Reliable Transport Protocol) opera sobre UDP e
implementa três mecanismos de controle de fluxo e erros:
Stop-and-Wait (SAW), Go-Back-N (GBN) e Selective Repeat (SR).

O cabeçalho de 9 bytes contém os campos:
  - SYN (1 bit): flag de estabelecimento de conexão
  - FIN (1 bit): flag de encerramento de conexão
  - SEQ (14 bits): número de sequência em pacotes (0 a 16383)
  - ACK flag (1 bit): indica que o campo ACK é válido
  - NACK (1 bit): negative acknowledgement
  - ACK (14 bits): número de acknowledgement
  - Length (8 bits): tamanho do payload; durante handshake,
    tamanho de janela proposto
  - CRC32 (32 bits): checksum sobre cabeçalho + payload

Pacotes com CRC32 inválido são descartados silenciosamente pelo
receiver, sem envio de NACK, pois nenhum campo do cabeçalho —
inclusive o SEQ — é confiável quando há corrupção. O timeout
fixo de 100 ms no sender dispara a retransmissão.

O handshake de três vias (SYN → SYN+ACK → ACK) negocia a janela
efetiva, definida como o mínimo entre as janelas propostas pelas
duas partes. O encerramento é two-way (FIN → FIN+ACK).

2. PARTE 1 — STOP-AND-WAIT
================================================================

----------------------------------------------------------------
2.1 Throughput Teórico Máximo
----------------------------------------------------------------

No SAW, o emissor aguarda o ACK antes de enviar o próximo
pacote. A eficiência do protocolo é dada por (Kurose & Ross,
Seção 3.4):

  η_SAW = (L/R) / (RTT + L/R) = 1 / (1 + 2a)

onde:
  L   = tamanho do pacote em bits
  R   = taxa do enlace em bps
  a   = T_prop / T_trans  (razão entre atraso de propagação
        e tempo de transmissão)
  RTT = round-trip time medido

Parâmetros da implementação:
  - Payload máximo: 255 bytes
  - Cabeçalho:        9 bytes
  - Tamanho total:  264 bytes = 2.112 bits por pacote
  - Taxa do enlace: Ethernet Gigabit = 10^9 bps
  - T_trans = 2112 / 10^9 ≈ 2,1 µs

2.4 Comportamento do CRC32
----------------------------------------------------------------

O CRC32 é calculado sobre o cabeçalho completo (com o campo CRC
zerado) concatenado com o payload. Pacotes corrompidos são
descartados silenciosamente pelo receiver sem envio de NACK,
pois nenhum campo — inclusive o SEQ — é confiável quando há
corrupção. O timeout de 100 ms no sender dispara a retransmissão.

[INSERIR: Demonstração com captura Wireshark.

Descreva:
(a) Como o pacote corrompido aparece na captura — por exemplo,
    ausência de ACK após o envio de determinado SEQ, seguida
    de retransmissão do mesmo SEQ após 100 ms (saw_crc.pcapng).

(b) O comportamento do sender: ao não receber ACK dentro do
    timeout, retransmite o mesmo pacote com o mesmo SEQ.

(c) O que ocorreria sem CRC32: o receiver aceitaria dados
    corrompidos como válidos, causando corrupção silenciosa do
    arquivo transferido sem qualquer possibilidade de detecção
    na camada de transporte. A aplicação receberia dados
    incorretos sem saber.]

Com janela de tamanho N, a eficiência do protocolo de janela
deslizante é (Kurose & Ross, Seção 3.4):

  η = N / (1 + 2a),   se N < 1 + 2a   (janela insuficiente)
  η = 1,              se N ≥ 1 + 2a   (janela suficiente)
